# Single-transaction v3 genesis

Direct creation is the default. The first input is an existing confirmed, token-free P2PKH wallet UTXO at output index zero. Its previous transaction ID is the CashToken category; the new genesis transaction ID is the public configuration's `genesis`. These identifiers are deliberately distinct.

The transaction creates output 0 with exactly one mutable state NFT and the initial state commitment, output 1 with the empty staking escrow, and output 2 with the complete reward reserve. RegistryV3 and AssetRoleV3 scripts and all immutable constructor parameters remain unchanged. Additional outputs return excess reward fungible tokens and BCH to the genesis input's wallet key. Unrelated fungible categories and all NFTs are excluded from wallet selection. The wallet scan and source proofs require two chipnet providers and confirmed inputs; no unconfirmed ancestry is introduced.

Direct genesis no longer needs a factory covenant witness. `validateGenesis` independently validates initial role scripts, state commitment, amounts, category separation, source outpoints, absence of input NFTs, token conservation and wallet-only change. Indexer replay applies these checks to both direct and legacy genesis before the existing VM, fee, canonical proof, lineage and transition checks. A genesis with a duplicated state NFT, extra minted tokens, incomplete reserve or changed role outputs cannot pass these checks. Pending genesis is displayed from its durable operation journal, while the canonical indexer continues to require confirmed genesis before enabling offers or claims.

The wallet reconstructs the complete plan and signing metadata before authorization. Cashonize receives one WizardConnect request with `broadcast:false`, all selected input derivation paths, full reserve, miner fee, carriers, change and immutable parameters. Submission reconstructs the plan again, rejects modified transaction shape, verifies Schnorr ALL|UTXOS|FORKID signatures and BCH2026 VM execution, and persists signed bytes before application broadcast. The fixed miner fee is 10,000 satoshis; covenant carriers total 3,000 satoshis. Token change can require another 1,000-satoshi carrier. Wallet selection is bounded to eight inputs.

The existing IndexedDB database, object store, keys and legacy records are preserved. New records use the optional `creationMode:direct` field; records without it continue through the original factory recovery flow. An explicitly labeled legacy creation button remains available when no suitable confirmed output zero exists. Direct creation never silently falls back or generates a preparation transaction.

Pending creations appear immediately with the genesis transaction ID and public configuration, survive reload, and are reconciled every 20 seconds while the page is idle. Canonical confirmations are shown with their count. Removed confirmations return to pending or uncertain status. Missing/dropped transactions and network failures retain the exact signed bytes; retries require an explicit action. A conflicting confirmed spend is labeled only after both providers prove the same conflicting transaction. Provider disagreement alone produces an uncertain status. No retry selects fresh coins, replaces a transaction, or requests an additional signature for a signed operation.

The change does not alter offer registration, ranking, earliest-registration tie-breaking, queue capacity, no-skipping, reward release/buffer, independent locks, caller-funded claims, refunds, withdrawals, or v1/v2 routes. No contract source or bytecode change is required. Mainnet remains disabled.

Verification uses real BCHN regtest with `acceptnonstdtxn=0`, local signatures over the actual Cashonize plans, all four asset pairs, the existing compatibility review gate, and read-only public chipnet checks. No funded public transaction or live Cashonize approval is performed. Actual device-specific Cashonize handling remains for user testing; unconfirmed transactions remain reversible until canonical confirmation. Discovery remains browser-local or configuration import, and browser storage should be backed up through the public recovery configuration.
